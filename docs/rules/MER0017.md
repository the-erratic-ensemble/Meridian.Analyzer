# MER0017

## Summary

`MER0017` flags async materialization calls where a visible `Where`, `Take`, or `Skip` bound is absent.

## Intent

Unbounded EF materialization can load large tables or relationship graphs into memory. Runtime code should make its query bounds visible near the materialization call.

## What It Reports

Reports:

- `ToListAsync()`
- `ToArrayAsync()`
- `ToDictionaryAsync()`
- `ToHashSetAsync()`

Approved locations include tests, `Migrations`, `Cli`, and `tools` paths.

The rule recognizes a query as bounded when the same invocation chain visibly includes `Where`, `Take`, or `Skip`, or when a materialized local variable, local reassignment, or helper method return was initialized from such a chain.

The rule also treats these as bounded for materialization-memory purposes:

- C# query expressions with a `where` clause.
- Aggregate materialization after `GroupBy`, because the result is the grouped projection.
- Raw SQL materialization when the SQL argument visibly contains a bounding term such as `WHERE`, `LIMIT`, `OFFSET`, `TOP`, or a `p_limit` parameter.
- Explicit full-read helpers whose method names declare complete-result semantics, catalogue/reference reads, report generation, or maintenance validation/repair. Their complete-result contract remains visible in the method name.

## Examples

Incorrect:

```csharp
var reports = await dbContext.Reports.ToListAsync(cancellationToken);
```

Correct:

```csharp
var reports = await dbContext.Reports
    .Where(report => report.TenantId == tenantId)
    .Take(100)
    .ToListAsync(cancellationToken);
```

### Dictionary Materialization

Incorrect:

```csharp
var tenants = await dbContext.Tenants
    .ToDictionaryAsync(tenant => tenant.Id, cancellationToken);
```

Correct:

```csharp
var tenants = await dbContext.Tenants
    .Where(tenant => tenant.IsActive)
    .Take(500)
    .ToDictionaryAsync(tenant => tenant.Id, cancellationToken);
```

### Array Materialization

Incorrect:

```csharp
var jobs = await dbContext.ReportJobs.ToArrayAsync(cancellationToken);
```

Correct:

```csharp
var jobs = await dbContext.ReportJobs
    .Where(job => job.TenantId == tenantId)
    .OrderByDescending(job => job.CreatedAt)
    .Take(50)
    .ToArrayAsync(cancellationToken);
```

## Preferred Refactor

Add a visible filter/page/limit, or move deliberate full-table maintenance flows behind a named maintenance helper and document why they are acceptable.

If the query is already bounded inside query syntax, a helper query method, aggregate SQL, or raw SQL text, make that bound visible enough for the analyzer. Duplicate runtime filters add no value.

Methods whose public contract means `all`, `full catalogue`, or `validate the complete graph` should keep their names honest and their full-read behavior explicit. Arbitrary caps would change that contract.
