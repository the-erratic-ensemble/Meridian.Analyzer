# MER0047

## Summary

`MER0047` flags direct delegate, event, and conditional delegate invocation inside a `lock` body.

## Intent

Callback code can re-enter shared state, block on another resource, or invoke arbitrary consumer code. Running it after the lock releases keeps callback ownership separate from shared-state synchronization.

## What It Reports

The rule resolves the invoked receiver and reports delegate-typed calls inside a lock body, including:

- `callback(...)`
- `callback.Invoke(...)`
- `callback?.Invoke(...)`
- event invocation

The lock expression itself is outside the lock body and remains outside this rule’s location boundary.

## What It Allows

- Normal method calls on owned objects.
- Capturing state while the lock is held and invoking a callback after the lock.
- Callback invocation outside a lock body.

## Examples

### Direct Callback

Incorrect:

```csharp
lock (_gate) {
    _state = state;
    notify?.Invoke(state);
}
```

Correct:

```csharp
State snapshot;
lock (_gate) {
    _state = state;
    snapshot = _state;
}

notify?.Invoke(snapshot);
```

### Event Notification

```csharp
StateChangedEventArgs args;
lock (_gate) {
    args = new StateChangedEventArgs(_state);
}

StateChanged?.Invoke(this, args);
```

## Analysis Scope

The analyzer uses the syntax lock body and the semantic type of the invoked receiver. It covers direct delegate-typed locals, fields, properties, and events in non-test paths. Invocations nested in lambdas and local functions are separate execution boundaries.

## Preferred Refactor

Capture the callback inputs under the lock, leave the lock, and invoke the delegate or event from the surrounding method scope.
